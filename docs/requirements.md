# Требования — Wishly

**Версия:** MVP  
**Аудитория:** B2C  
**Ориентир UX:** Amazon Wishlist  
**Язык интерфейса:** русский (RU only)  
**Масштаб:** сотни пользователей  

---

## Overview

**Wishly** — рабочее название сервиса вишлистов подарков (имя может быть изменено на gate утверждения требований).

Продукт решает задачу: пользователь создаёт один или несколько вишлистов с желаемыми подарками (ссылки, цены, изображения), делится прямой ссылкой с близкими, а гости по ссылке просматривают список и **бронируют** подарки после регистрации, чтобы избежать дублей. Владелец получает уведомления о бронированиях; у вишлиста есть дата события и дедлайн бронирования.

### Состав MVP

| Возможность | В MVP |
|-------------|-------|
| Регистрация и авторизация | Да |
| Несколько вишлистов на пользователя | Да |
| Категории подарков | Да |
| Подарки: название, ссылка, цена; опционально изображение и заметка | Да |
| Публичная ссылка на вишлист (view + book) | Да |
| Бронирование подарка (только зарегистрированным) | Да |
| Комментарии к вишлисту/подаркам среди авторизованных пользователей | Да |
| Дата события и дедлайн бронирования | Да |
| Уведомления владельцу о бронировании (email + in-app) | Да |
| Роль администратора (в т.ч. отмена брони) | Да |
| Soft delete вишлистов и подарков | Да |
| Изображения: URL и загрузка файла | Да |
| Mobile-first UI | Да |

Вне MVP (не реализуется в первой итерации, если не согласовано отдельно): анонимное бронирование, комментарии/лайки на публичной странице шаринга, мультиязычность, SSO, push-уведомления, расширенная аналитика.

## User Roles

### Роли

| Роль | Описание |
|------|----------|
| **Пользователь (Owner / зарегистрированный пользователь)** | Владеет своими вишлистами; может создавать/редактировать/удалять (soft) вишлисты и подарки; комментировать в своих вишлистах; бронировать подарки в чужих вишлистах по share-ссылке после входа. |
| **Гость по ссылке (Guest-by-link)** | Открыл публичную share-ссылку. Без аккаунта: только просмотр. Для бронирования обязан зарегистрироваться / войти. На публичной странице: **только просмотр и бронирование** (без комментариев и лайков). |
| **Администратор (Admin)** | Платформенная роль: видит имя бронирующего; может отменять / снимать бронирование; доступ к операционным действиям модерации в рамках MVP (см. матрицу). |

### Матрица прав

| Действие | Owner (свои данные) | Guest-by-link (без входа) | Зарегистрированный гость (по share) | Admin |
|----------|---------------------|---------------------------|--------------------------------------|-------|
| Регистрация / вход | — | Да (чтобы бронировать) | Уже вошёл | Да |
| CRUD своих вишлистов | Да | Нет | Нет | Просмотр / soft delete по необходимости модерации |
| CRUD своих подарков | Да | Нет | Нет | Soft delete / модерация |
| Управление категориями своих вишлистов | Да | Нет | Нет | Нет (или просмотр) |
| Комментарии к своим вишлистам/подаркам | Да | Нет | Нет | Да (модерация: просмотр / удаление) |
| Просмотр публичного вишлиста по ссылке | Да | Да | Да | Да |
| Бронирование подарка по ссылке | Да* | Нет | Да | Да* |
| Видеть имя бронирующего | Да (на своих вишлистах) | Нет | Нет | Да |
| Отмена / снятие бронирования | Да (со своих подарков) | Нет | Да (своя бронь до дедлайна) | Да |
| Настройка даты события / дедлайна | Да | Нет | Нет | Нет |

\* Зарегистрированный пользователь может бронировать в чужом вишлисте по ссылке; бронирование своих подарков владельцем запрещено.

### Области CRUD (сводка)

| Сущность | Create | Read | Update | Delete |
|----------|--------|------|--------|--------|
| User (свой профиль) | Регистрация | Свой / Admin | Свой | Soft / Admin |
| Wishlist | Owner | Owner; Guest по ShareLink (ограниченно); Admin | Owner | Soft: Owner / Admin |
| Category | Owner (в рамках своего wishlist) | Owner; на share — без управления | Owner | Soft или hard в рамках wishlist Owner |
| Gift / Item | Owner | Owner; Guest по ShareLink; Admin | Owner | Soft: Owner / Admin |
| Booking | Зарегистрированный гость (по share) | Owner (своего wishlist), Admin, сам booker (своя бронь) | Admin (отмена) | Admin (снятие); soft-связка с Gift |
| Comment | Owner (свои wishlist/item); Admin (модерация) | Owner, Admin | Автор / Admin | Автор / Admin |
| Notification | Система | Получатель (Owner) | Mark read — получатель | Soft / auto-retention |
| ShareLink | Owner (при публикации wishlist) | Публичный по токену | Owner (ротация / отзыв) | Owner / Admin |

| Поле | Тип / ограничения | Обязательность |
|------|-------------------|----------------|
| `id` | UUID | Да |
| `email` | уникальный, для входа и уведомлений | Да |

| Поле | Тип / ограничения | Обязательность |
|------|-------------------|----------------|
| `id` | UUID | Да |
| `owner_id` | FK → User | Да |

| `description` | текст | Нет |

| `booking_deadline` | дата/время, до которого доступно бронирование | Да (MVP) |

| Поле | Тип / ограничения | Обязательность |
|------|-------------------|----------------|
| `id` | UUID | Да |
| `gift_id` | FK → Gift, уникальность активного бронирования | Да |
| `booker_id` | FK → User | Да |
| `status` | `active` \| `cancelled` | Да |

| Поле | Тип / ограничения | Обязательность |

| Поле | Тип / ограничения | Обязательность |
|------|-------------------|----------------|
| `id` | UUID | Да |

### Диаграмма связей (логическая)

```text
User 1──N Wishlist 1──N Category
              │
              1──N Gift 0..1 Booking N──1 User(booker)
              │         │
              │         └── Comment (gift-level, auth only)
              └── Comment (wishlist-level, auth only)
              └── ShareLink
User 1──N Notification
```

## Business Rules

### Регистрация и доступ

1. Бронирование доступно **только зарегистрированным** пользователям (анонимная бронь запрещена).
2. Публичная share-страница: просмотр списка подарков и статусов бронирования; действия — вход/регистрация и бронирование свободного подарка.
3. Комментарии — только в авторизованном контексте владельца вишлиста (не на публичной share-странице).

### Бронирование

4. Один подарок может иметь не более **одного активного** бронирования.
5. Попытка забронировать уже забронированный подарок — отказ с понятной ошибкой.
6. Имя бронирующего видно **владельцу вишлиста** и **администратору**; прочим гостям — только факт брони.
7. Снять бронирование (`status = cancelled`) могут: **Admin**, **владелец** вишлиста (со своих подарков), **booker** (свою бронь до `booking_deadline`). После отмены подарок снова доступен для брони (если не истёк дедлайн и сущность не удалена).
8. Бронирование своего подарка владельцем в своём вишлисте — запрещено.

### Дата события и дедлайн

9. У вишлиста обязательны `event_date` и `booking_deadline`.
10. После `booking_deadline` создание новых бронирований запрещено; уже созданные активные брони сохраняются.
11. `booking_deadline` не должен быть позже `event_date` (валидация при сохранении).

### Soft delete

12. Удаление Wishlist и Gift — **soft delete** (`deleted_at`). Soft-deleted сущности скрыты из обычных списков и публичного share; связанные активные бронирования не показываются гостям как доступные.
13. Восстановление soft-deleted wishlist/gift в MVP: **Owner** (свои) и **Admin**.

### Share

14. ShareLink даёт доступ только к конкретному wishlist.
15. Owner может отозвать / деактивировать ссылку; после отзыва публичный доступ прекращается (нужна новая ссылка).

### Изображения

16. Изображение подарка: либо внешний URL, либо загруженный файл (допустимы оба способа; можно заменить одно другим).
17. Хранение загрузок: локальное файловое хранилище **или** S3-compatible — допущение MVP (см. Integrations).

### Уведомления

18. При создании бронирования владелец вишлиста получает **email** и **in-app** уведомление.
19. При отмене бронирования (Admin / Owner / booker) — владельцу уходит уведомление (email + in-app) о снятии брони; booker при отмене Admin/Owner также получает in-app (email — желательно).

### Лимиты MVP

20. Не более **20** вишлистов на пользователя.
21. Не более **200** подарков на вишлист.
22. Размер загружаемого изображения — до **5 МБ**; типы: jpeg/png/webp.

## Workflows

### Happy path: владелец

1. Пользователь регистрируется и входит.
2. Создаёт вишлист (название, описание опционально, `event_date`, `booking_deadline`).
3. Создаёт категории (опционально).
4. Добавляет подарки: title, url, price; опционально image (URL/файл), notes; привязка к категории.
5. При необходимости комментирует wishlist/gift в своём кабинете.
6. Получает / копирует ShareLink и отправляет друзьям.
7. Получает email + in-app уведомление, когда кто-то забронировал подарок; видит имя бронирующего.

### Happy path: гость → бронирование

1. Гость открывает ShareLink → видит вишлист (без комментариев).
2. Выбирает свободный подарок → система требует вход / регистрацию.
3. После входа подтверждает бронирование.
4. Подарок помечается «Забронировано»; другим гостям имя booker не видно.
5. Владелец получает уведомления.

### Альтернативы и ошибки

| Сценарий | Поведение |
|----------|-----------|
| Подарок уже забронирован | Отказ; UI показывает недоступность |
| Дедлайн бронирования истёк | Кнопка брони недоступна; API — 4xx |
| ShareLink отозван / неактивен | 404 / «ссылка недоступна» |
| Wishlist / Gift soft-deleted | Не видны в публичном и обычном UI |
| Неверные учётные данные | Ошибка входа, без раскрытия лишних деталей |
| Загрузка недопустимого файла изображения | Ошибка валидации типа/размера |
| Admin отменяет бронь | Статус cancelled; подарок снова свободен (если дедлайн позволяет); уведомление owner |

### Workflow Admin (MVP)

1. Admin входит с ролью `admin`.
2. Находит wishlist / gift / booking (операционный доступ).
3. Видит имя booker; при необходимости отменяет бронирование.

## NFR

### Язык и UX

- Интерфейс **только на русском**.
- **Mobile-first**; ориентация на паттерны Amazon Wishlist (список желаний, шаринг, статус брони).
- Основные сценарии (создание wishlist, добавление gift, шаринг, бронь) должны быть удобны на узком экране.

### Масштаб и производительность

- Ожидаемая нагрузка: **сотни пользователей**, умеренное число wishlist/gift на пользователя.
- Пагинация списков подарков при росте длины wishlist.
- Share-страница должна открываться быстро на мобильном (оптимизация изображений — по возможности).

### Безопасность (базовый контур auth)

- Регистрация / вход по email + пароль; пароли только в виде хеша (современный KDF, например bcrypt/argon2 — на этапе реализации).
- Сессии или JWT с разумным TTL; защита от CSRF для cookie-сессий (если применимо).
- Share-токены: криптостойкая случайная строка, неперечислимые URL.
- Разграничение прав Owner / Guest / Admin на API.
- Имя booker не отдавать в публичных API share-страницы.
- Ограничение размера/типа загружаемых изображений; без исполнения пользовательских файлов.
- HTTPS в прод-окружении (допущение деплоя).

### Надёжность уведомлений

- In-app уведомление создаётся атомарно с успешным бронированием (или сразу после в той же бизнес-операции).
- Email: best-effort с логированием ошибок доставки; повторные попытки — по возможности в MVP.

### Доступность и прочее

- Базовая читаемость форм и контраст на mobile; полноценный a11y-аудит — вне жёсткого MVP, без блокировки релиза.
- Offline mode — не требуется.

## Утверждённые решения (gate requirements)

1. Снятие брони: **Admin**, **владелец** (со своих подарков), **booker** (свою бронь до дедлайна).
2. Admin: **seed** при первом деплое (учётка в конфиге/env).
3. Restore soft-delete: **да** — Owner своих + Admin.
4. Комментарии: пишет только **owner** у своих wishlist/gift; Admin может удалять (модерация).
5. Лимиты MVP: до **20** вишлистов на user, до **200** подарков на wishlist, изображение до **5 МБ**.
6. Валюта: только **RUB**.
7. Audit log действий Admin: **вне MVP**.
8. Требования утверждены пользователем.
